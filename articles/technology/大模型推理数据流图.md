# 大模型推理全过程：矩阵 Shape、Batch 与多卡通信

以 Qwen3-8B 为例，把一次完整的大模型推理从输入一直顺到输出。模型参数固定为 36 层 Transformer，hidden size `H=4096`，32 个 Query Head，8 个 KV Head，每个 Head 的维度 `D=128`，所以 Query 的总维度是 `32 x 128 = 4096`，Key 和 Value 的总维度分别是 `8 x 128 = 1024`。FFN 的 intermediate size 是 `12288`，词表大小 `V=151936`。下面统一用 `B` 表示 batch size，`S` 表示 prompt sequence length，`T` 表示当前这一轮真正送进模型计算的 token 数，`L` 表示 Decode 时已经存在于 KV Cache 中的上下文长度。所有 Linear 都按照数学上的 GEMM 写法表示，即：

`[M,K] x [K,N] -> [M,N]`

PyTorch 实际保存 Linear weight 时通常是 `[N,K]`，这里只是为了方便理解矩阵乘法，统一按照 `[K,N]` 来写。

用户输入首先经过 tokenizer 得到 `input_ids`，shape 是 `[B,S]`。Embedding Table 的大小是 `[151936,4096]`，根据每一个 token id 查表以后得到 hidden states，shape 为 `[B,S,4096]`。进入真正的 Transformer 计算以后，框架通常不会一直把这个 Tensor 理解成三维的 `[B,S,H]`，而是把当前所有需要计算的 token flatten 到一起，形成 `[T,4096]`。对于最简单的 Prefill，如果 batch 中每个请求长度都相同，那么 `T = B x S`。例如 batch size 是 4，每个请求有 2048 个 prompt token，那么这一轮一共有 `4 x 2048 = 8192` 个 token，进入 Linear 的矩阵就是 `[8192,4096]`。如果 batch size 是 1、8、16，对应的就是 `[2048,4096]`、`[16384,4096]`、`[32768,4096]`。所以 batch size 本身并不会改变模型权重的 shape，它改变的是 GEMM 左矩阵的第一维，也就是这一轮同时处理多少 token。到了 Continuous Batching 和 Chunked Prefill 中，`T` 甚至不一定等于 `B x S`，而应该理解成这一轮 scheduler 实际调度进来的 token 总数。例如两个请求各做 512 个 Prefill token，同时还有两个请求各 Decode 一个 token，那么 `T = 512 + 512 + 1 + 1 = 1026`，这一层真正看到的输入就是 `[1026,4096]`。

现在进入第一层 Transformer。输入 `X` 是 `[T,4096]`，先经过 RMSNorm。RMSNorm 只在 hidden 维度上进行归一化，参数大小是 `[4096]`，所以输入和输出都是 `[T,4096]`。然后进入 QKV Projection。Q Projection 是：

`[T,4096] x [4096,4096] -> [T,4096]`

因为模型有 32 个 Query Head，每个 Head 是 128 维，所以 Q 的总维度正好是 `32 x 128 = 4096`。K Projection 是：

`[T,4096] x [4096,1024] -> [T,1024]`

V Projection 同样是：

`[T,4096] x [4096,1024] -> [T,1024]`

如果实现中把 QKV Projection 融成一个 GEMM，那么可以直接理解成：

`[T,4096] x [4096,6144] -> [T,6144]`

其中输出的前 4096 维属于 Q，接下来 1024 维属于 K，最后 1024 维属于 V，也就是 `4096 + 1024 + 1024 = 6144`。

QKV 生成以后，要重新解释成 Head 的形式。Q 从 `[B,S,4096]` reshape 成 `[B,32,S,128]`，K 和 V 分别从 `[B,S,1024]` reshape 成 `[B,8,S,128]`。这里有 32 个 Q Head，但是只有 8 个 KV Head，因此这是 GQA，每 4 个 Q Head 共用一个 K Head 和一个 V Head。随后进行 QK Norm 和 RoPE，这些操作不会改变矩阵 shape，所以完成以后 Q 仍然是 `[B,32,S,128]`，K 和 V 仍然是 `[B,8,S,128]`。

接下来是 Attention。Prefill 阶段假设 `B=4，S=2048`，那么 Q 的逻辑 shape 是 `[4,32,2048,128]`，K 是 `[4,8,2048,128]`，V 是 `[4,8,2048,128]`。考虑 GQA 的共享关系以后，每个 Query Head 都会找到对应的 KV Head。数学上 Q 和 `K^T` 相乘以后：

`[B,32,S,128] x [B,32,128,S] -> [B,32,S,S]`

所以 Attention Score 的逻辑 shape 是 `[B,32,S,S]`。代入 `B=4，S=2048`，就是：

`[4,32,2048,2048]`

然后在最后一个维度做 Softmax，再乘 V，输出恢复为 `[B,32,S,128]`，把 32 个 Head 拼回来以后就是 `[B,S,4096]`，重新 flatten 就又回到了 `[T,4096]`。这里必须区分“数学上的矩阵 shape”和“显存里实际存在的 Tensor”。普通 Attention 按数学定义确实会产生 `[B,32,S,S]`，但是 FlashAttention 不会真的把完整的 `S x S` Attention Matrix 写回 HBM，而是把 Q、K、V 分块加载，在片上存储中完成 QK、online softmax 和乘 V。因此我们理解计算关系时仍然使用 `[B,32,S,S]`，但分析显存占用时不能直接认为这个矩阵完整常驻显存。

Attention 的输出拼接以后是 `[T,4096]`，然后进入 O Projection。单卡情况下就是：

`[T,4096] x [4096,4096] -> [T,4096]`

再和进入 Attention 之前的 residual 相加，得到的仍然是 `[T,4096]`。接下来进入第二个 RMSNorm，shape 不变，仍然是 `[T,4096]`。然后进入 FFN。Qwen3 使用 SwiGLU，因此有 Gate Projection 和 Up Projection 两个分支。Gate 是：

`[T,4096] x [4096,12288] -> [T,12288]`

Up 也是：

`[T,4096] x [4096,12288] -> [T,12288]`

随后计算：

`SiLU(Gate) x Up`

这里是逐元素乘法，所以结果仍然是 `[T,12288]`。最后通过 Down Projection 把 intermediate dimension 压回 hidden dimension：

`[T,12288] x [12288,4096] -> [T,4096]`

再与 residual 相加，最终得到 `[T,4096]`。到这里一个完整 Transformer Layer 结束。下一层继续接收这个 `[T,4096]`，因此 36 层的主干实际上一直是在做：

`[T,4096] -> [T,4096]`

只是在每一层内部先展开成 QKV 和 12288 维 FFN，再重新压回 4096。

如果使用两张 GPU 做 Tensor Parallel，真正需要理解的是这些矩阵在哪个维度切。TP=2 时，每张 GPU 都持有完整的输入 hidden states `[T,4096]`，但是 QKV Projection 的输出维度被切开。Q 原本是 `[T,4096]`，GPU0 只计算其中一半 `[T,2048]`，对应 16 个 Q Head，GPU1 计算另外 16 个 Q Head。K 原本是 `[T,1024]`，每张 GPU 得到 `[T,512]`，也就是各 4 个 KV Head；V 同样各得到 `[T,512]`。

因此 GPU0 上实际发生的是：

`Q: [T,4096] x [4096,2048] -> [T,2048]`

`K: [T,4096] x [4096,512] -> [T,512]`

`V: [T,4096] x [4096,512] -> [T,512]`

GPU1 计算另外一半，shape 完全一样。每张 GPU 都使用完整的 `[T,4096]` 输入，但是只生成属于自己的 Heads。这种方式就是 Column Parallel Linear。因为两个 GPU 计算的是输出维度中互不重叠的部分，所以 QKV Projection 完成以后不需要 AllReduce。

Attention 也不需要通信。TP=2 时 GPU0 本地有 16 个 Q Head、4 个 K Head 和 4 个 V Head，逻辑 shape 分别是 `[B,16,S,128]`、`[B,4,S,128]`、`[B,4,S,128]`；GPU1 有另外一半。每 4 个 Q Head 对应一个 KV Head，所以两个 GPU 都可以独立完成自己负责的 GQA Attention。GPU0 最终得到 16 个 Attention Head，拼起来是 `[T,2048]`，GPU1 同样得到 `[T,2048]`。因此整个 QKV Projection、RoPE、Attention 过程都不需要两张 GPU 交换 Head 数据。

第一次真正重要的 TP 通信发生在 O Projection。单卡原本是：

`[T,4096] x [4096,4096] -> [T,4096]`

但是现在 GPU0 只有前 2048 维 Attention Output，GPU1 只有另外 2048 维，所以 O Projection 做 Row Parallel。GPU0 计算：

`[T,2048] x [2048,4096] -> [T,4096]`

得到一个 Partial Output。GPU1 同样计算：

`[T,2048] x [2048,4096] -> [T,4096]`

得到另一个 Partial Output。完整 O Projection 的结果等于两个 Partial Output 相加：

`O = Partial_GPU0 + Partial_GPU1`

因此这里需要执行一次 NCCL AllReduce SUM。AllReduce 结束以后，两张 GPU 上重新都有完整的 `[T,4096]`，这样才能继续做 residual 和后面的 RMSNorm。这是一个 Transformer Layer 中第一次核心 TP 通信。

接下来 FFN 采用完全类似的切法。Gate Projection 和 Up Projection 都按输出维度做 Column Parallel。完整 Gate 原本是：

`[T,4096] x [4096,12288] -> [T,12288]`

TP=2 后 GPU0 只计算：

`[T,4096] x [4096,6144] -> [T,6144]`

GPU1 计算另外一半。Up Projection 完全一样，所以两个 GPU 分别持有自己的 Gate `[T,6144]` 和 Up `[T,6144]`。随后每张 GPU 本地计算 `SiLU(Gate) x Up`，结果仍然是 `[T,6144]`。整个过程没有通信，因为 FFN intermediate dimension 本身就是可以切开的。

到了 Down Projection，又遇到了和 O Projection 一样的问题。完整计算应该是：

`[T,12288] x [12288,4096] -> [T,4096]`

现在每张 GPU 只有 6144 个 intermediate dimensions，因此 GPU0 做：

`[T,6144] x [6144,4096] -> [T,4096]`

GPU1 做另外一半，二者得到的都是 Partial Output。最后必须把两个 Partial Output 相加，因此执行第二次 NCCL AllReduce SUM，得到完整的 `[T,4096]`。再完成 residual add，一个 Transformer Layer 结束。

因此两卡 Tensor Parallel 下，一层的通信模式可以直接记成：RMSNorm 无通信，QKV Column Parallel 无通信，RoPE 无通信，Attention 每卡独立计算无通信，O Projection 做 Row Parallel，结束以后一次 AllReduce；第二个 RMSNorm 无通信，Gate 和 Up 做 Column Parallel，无通信，SwiGLU 本地计算，Down Projection 做 Row Parallel，结束以后再一次 AllReduce。

也就是：

`1 Transformer Layer = 2 次主要 TP AllReduce`

Qwen3-8B 有 36 层，因此一次完整 forward 的 Transformer 主干是：

`36 x 2 = 72 次主要 AllReduce`

这也是理解多卡推理性能的关键：Tensor Parallel 把每张 GPU 的 GEMM 计算量切小了，但是引入了每层两次同步通信。

Prefill 完成 36 层以后，得到的仍然是 `[T,4096]`。经过 Final RMSNorm 后 shape 不变。对于普通生成场景，并不需要对 prompt 中每一个位置都计算最终词表概率，只需要取每个请求最后一个有效 token 对应的 hidden state，因此可以从 `[B,S,4096]` 中取出 `[B,4096]`。然后进入 LM Head：

`[B,4096] x [4096,151936] -> [B,151936]`

得到每个请求对整个词表的 logits。再经过 temperature、top-k、top-p 或其他 sampling 策略，每个请求最终选出一个 token，因此输出 token ids 的 shape 是 `[B]`。这批新 token 随后重新进入 Embedding，开始第一轮 Decode。

Decode 和 Prefill 最大的区别是当前轮真正参与模型计算的新 token 数发生了变化。假设 batch size 是 4，四个请求都在生成阶段，那么每一个请求本轮只新增一个 token，因此 `T=B=4`。进入 Transformer 的 hidden states 不再是 Prefill 时的 `[8192,4096]`，而只是 `[4,4096]`。Q Projection 变成：

`[4,4096] x [4096,4096] -> [4,4096]`

K 和 V 分别是 `[4,1024]`。reshape 以后新的 Q 是 `[4,32,1,128]`，新的 K 和 V 是 `[4,8,1,128]`。

但是 Attention 不能只使用这个新 token 的 K 和 V，因为它需要看到之前所有 token，因此每层都维护 KV Cache。假设当前上下文已经有 `L=2048` 个 token，那么逻辑上的 K Cache 和 V Cache 分别是：

`K Cache = [4,8,2048,128]`

`V Cache = [4,8,2048,128]`

新的 K、V 写入 Cache 后变成：

`K Cache = [4,8,2049,128]`

`V Cache = [4,8,2049,128]`

此时 Q 是 `[4,32,1,128]`，它和整个历史 K 做 Attention，因此 Attention Score 的逻辑 shape 从 Prefill 的：

`[4,32,2048,2048]`

变成：

`[4,32,1,2049]`

也就是说，Decode 的 Attention 本质上是：

`[B,32,1,128] x [B,32,128,L] -> [B,32,1,L]`

再乘历史 V：

`[B,32,1,L] x [B,32,L,128] -> [B,32,1,128]`

最后把 Heads 拼起来得到 `[B,4096]`，然后继续经过 O Projection、FFN 和下一层。

因此 Prefill 和 Decode 的 GEMM 差别可以直接从第一维看出来。还是 `B=4，S=2048` 的例子，Prefill 时 Linear 的主要输入是：

`[8192,4096]`

Decode 时则变成：

`[4,4096]`

模型权重完全没有变化。Q Projection 始终使用 `[4096,4096]`，Gate 和 Up 始终使用 `[4096,12288]`，Down 始终使用 `[12288,4096]`。真正改变的是左矩阵中参与计算的 token 数，也就是 GEMM 的 M 维。

因此 Prefill 可以形成很大的 GEMM，GPU Tensor Core 比较容易被喂满，通常表现为更明显的 compute-bound；Decode 每次每请求只增加一个 token，GEMM 的 M 维很小，GPU 计算单元不容易充分利用，同时每一层又必须读取越来越长的 KV Cache，所以更容易受到 HBM bandwidth、kernel launch latency 和跨卡通信 latency 的影响。

KV Cache 的大小也可以直接从矩阵维度算出来。Qwen3-8B 每个 token 在每一层需要保存 8 个 K Head 和 8 个 V Head，每个 Head 是 128 维，因此一个 token 一层需要保存：

`2 x 8 x 128 = 2048 个元素`

如果使用 BF16，每个元素 2 Bytes，也就是：

`2048 x 2 Bytes = 4096 Bytes = 4 KB`

所以是每 token 每 layer 约 4 KB。模型一共有 36 层，因此一个 token 的完整 KV Cache 大约是：

`4 KB x 36 = 144 KB / token`

如果当前系统总共维护 32768 个有效 token，那么理论 KV Cache 大约是：

`32768 x 144 KB ≈ 4.5 GB`

TP=2 时 KV Head 被分到两张 GPU，每张卡只有 4 个 KV Head，所以每卡 KV Cache 大致减半，每 token 约 72 KB，32768 token 对应每张卡约 2.25 GB。真实 vLLM 的物理布局不会简单保存成连续的 `[B,8,L,128]`，而是使用 PagedAttention，把 KV Cache 组织成固定大小的 block/page，并通过 block table 建立逻辑 sequence 到物理 KV block 的映射。但在理解 Attention 数学关系时，始终可以把它看成逻辑上的：

`[B,Num_KV_Heads,L,Head_Dim]`

在这里就是：

`[B,8,L,128]`

Decode 阶段两卡 TP 的切分方式和 Prefill 完全相同。GPU0 持有 16 个 Q Head 和 4 个 KV Head，GPU1 持有另外 16 个 Q Head 和 4 个 KV Head，因此每张 GPU 独立从自己的 KV Cache 读取数据并完成 Attention，不需要在 Attention 内交换 K/V。Attention 完成以后，每张 GPU 得到 `[B,2048]`，进入 O Projection，各自计算出 `[B,4096]` Partial Result，然后做一次 AllReduce；FFN 中每张 GPU 得到 `[B,6144]` intermediate states，Down Projection 后再次得到 `[B,4096]` Partial Result，再做一次 AllReduce。

也就是说，虽然 Decode 的 GEMM 从 Prefill 的 `[8192,4096]` 缩小到了 `[4,4096]`，但 36 层仍然要经历每层两次 TP collective，也就是主干仍然存在 72 次 AllReduce。正因为计算变小了而同步次数没有减少，多卡 Decode 很容易出现通信延迟占比明显上升的问题。这也是为什么两张 GPU 并不意味着 Decode 性能直接翻倍。如果 batch 很小，单卡计算本来只需要很短时间，而跨卡 collective、kernel launch 和同步本身就有固定延迟，最后很可能只能得到远低于 2 倍的加速，甚至在某些配置下比单卡还慢。

batch size 对矩阵大小的影响也可以统一起来理解。如果是纯 Decode，假设所有请求每轮都生成一个 token，那么：

`Batch=1  -> Linear Input = [1,4096]`

`Batch=4  -> Linear Input = [4,4096]`

`Batch=16 -> Linear Input = [16,4096]`

`Batch=64 -> Linear Input = [64,4096]`

对应的 Q 分别是 `[1,4096]`、`[4,4096]`、`[16,4096]`、`[64,4096]`，Gate 和 Up 分别是 `[1,12288]`、`[4,12288]`、`[16,12288]`、`[64,12288]`。

所以增加 Decode batch size 的本质，是增大所有 GEMM 的 M 维。权重矩阵 `[4096,4096]`、`[4096,12288]` 这些东西并没有变化，但是一次加载这些权重之后可以同时给更多 token 使用，因此能够增加 weight reuse，提高 GPU utilization。但是 batch 越大，同时存在的请求越多，KV Cache 占用也越高，每轮 Attention 需要读取的 KV 总量也会上升，因此 batch 不可能无限增加。

对于实际的 vLLM 或 SGLang，最准确的视角不是死盯着 `B x S`，而是看每一个 iteration 中 scheduler 到底发下来多少 scheduled tokens。假设这一轮 Request A 做 512 个 Prefill token，Request B 做 256 个 Prefill token，另外 32 个正在 Decode 的请求各处理 1 个 token，那么：

`T = 512 + 256 + 32 = 800`

进入第一层的矩阵就是 `[800,4096]`，Q 是 `[800,4096]`，K 和 V 各是 `[800,1024]`，Gate 和 Up 各是 `[800,12288]`。Linear 层基本只关心这些 token 被 packed 以后得到的 `T`。Attention 则需要结合 sequence length、position、slot mapping、block table 等 metadata，知道这些 token 分别属于哪个 sequence，以及应该读取哪一段历史 KV Cache。这就是 Continuous Batching 能够把不同长度、不同阶段的请求放到一次 forward 中执行的基础。

  ↓

[B,32,1,L]

Attention x V
  ↓
[B,32,1,128]

O Projection
  ↓
AllReduce
  ↓

  ↓

真正需要记住的主线就是：**模型的权重矩阵尺寸在推理过程中基本是固定的，真正不断变化的是 GEMM 的 M 维，也就是当前 iteration 处理的 token 数 `T`。Prefill 的 `T` 很大，所以主要形成大 GEMM；Decode 的 `T` 接近 active batch size，所以主要是小 GEMM，但与此同时每一层都需要读取长度不断增长的 KV Cache。Tensor Parallel 则把 QKV、Gate、Up 这些 Linear 做 Column Parallel，把 O Projection 和 Down Projection 做 Row Parallel，因此每一层主要产生两次 AllReduce。Qwen3-8B 一共 36 层，所以一次完整经过 Transformer 主干就对应 72 次主要 TP collective。**
